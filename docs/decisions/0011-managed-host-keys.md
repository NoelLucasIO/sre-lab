# ADR 0011: VM host keys are managed by Terraform and outlive the VMs

**Status:** accepted (2026-11-11) · **Phase:** 4 · Amends [ADR 0002](0002-state-layering.md) (one remote-state read)

## Context

- The runner, Ansible, `seed-secret.sh` and `restore-k3s.sh` all check the k3s VMs' SSH host keys strictly against `ci/runner/known_hosts`. That is deliberate: no trust-on-first-use on the LAN.
- The keys were generated by each VM on first boot. Rebuilding a VM therefore always changed its identity, and every rebuild needed a human to verify and re-pin three keys.
- In the [DR drill of 2026-11-11](../drills/2026-11-11-dr-drill.md) that took **6 min 4 s of a 23 min 10 s RTO**. Verifying the new keys out-of-band was itself hard: no console login, the guest agent's file commands are blocked on Rocky 9, and `virt-cat` needs `LIBGUESTFS_BACKEND=direct` to read a running VM's disk. The runner's copy of `known_hosts` had also drifted from the repo's.

## Decision

- `envs/lab-base` generates an ED25519 key pair per k3s VM (`tls_private_key`, `prevent_destroy`). It is the layer that already holds long-lived artifacts and is never destroyed by a rebuild of `envs/lab`.
- `envs/lab` reads them through `terraform_remote_state` (two outputs: public keys readable, private keys sensitive) and passes them to the VM module, which hands them to cloud-init (`ssh_keys`). A rebuilt VM boots with the same identity.
- `envs/lab` outputs `known_hosts`, and `ci/runner/known_hosts` is that output, committed. The nightly drift check fails if they differ; the k3s workflow installs the repo copy on the runner before every converge.

## Consequences

- A destroy-and-rebuild of `envs/lab` needs no host-key work: the DR drill's longest step disappears.
- This amends ADR 0002 in one place: `envs/lab` now reads `envs/lab-base` state. Both roots already use the same Postgres credentials, so no new access is granted, but `envs/lab` can no longer be planned without `lab_base` state present. A missing key falls back to the old behaviour with a warning (`check "host_keys_managed"`), so the first rollout can plan `envs/lab` before `envs/lab-base` is applied.
- Private host keys now exist in three more places, all on fedora or in its database: the `lab_base` Terraform state, the VMs' cloud-init ISOs in the `990Flash` pool, and the provider's ISO cache under `/tmp`. They are host keys for three lab VMs; anyone who can read those places is already root-equivalent on fedora.
- Plans show `user_data` as `(sensitive value)`. The VM's `instance-id` is computed from the non-secret parts plus the public key, so it stays readable and still changes whenever the cloud-init config changes.
- Rotating a key is deliberate (`prevent_destroy` must be lifted, then `-replace`), followed by re-rendering `known_hosts` ([runbook](../runbooks/host-keys.md)).

## Alternatives

- **Keep first-boot keys, re-pin with `ssh-keyscan` after a rebuild:** trust-on-first-use, the thing the pinning exists to prevent.
- **Generate the keys inside `envs/lab`:** a destroy of `envs/lab` (the drill scenario) would destroy them too.
- **Keep them outside Terraform (files or Podman secrets on fedora):** a second source of truth to keep in step with the VM definitions, and nothing to drift-check against.
